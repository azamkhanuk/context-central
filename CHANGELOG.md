# Changelog

Each release of context-central, newest first. The version is the one in `.claude-plugin/plugin.json`. An installed copy stays on its release until `claude plugin update` finds a newer one under the id it was installed as, `context-central@azamkhanuk` or, for a copy installed before 0.14.0, `context-central@context-central`, or until auto-update does where that is on.

## 0.21.0 - 2026-11-25

Research stands alone. What it finds is kept as a research, a folder of its own in the map of numbered facts with every source saved beside them, which later runs add to, check against the code and against a spec, a design or a diff, and copy out for another planner. A run writes its brief first, gathers in rounds through agents that only read, and stops by a test it names, and it can be left to run with nobody there. An estate extends it through its settings, and the research skill installs by itself, with no plugin, from a clone or with a package each release carries. `docs/research.md` has the whole of it.

- **A research folder.** `context-central research new <name> [--title <title>] [--item <item>] [--json]` makes `research/<name>/` in the map: the fact sheet `index.md`, the research brief `brief.md`, the log `log.md`, the set-aside list `set-aside.md`, the reading `reading.md` and an empty `sources/`, and prints the place of the fact sheet. Where git tracks the map's settings, a second line says whether git keeps the folder or ignores it. The folder is the plugin's own, as the work folder is, whatever `nodeDirs` lists, and a folder an estate keeps there already is never taken for a research: a research is told by the head of its `index.md`. An estate that keeps something else under that name gives research another folder with `researchDir`. With an item, the state file links the fact sheet; with none, the note of each repo it is about does.
- **Facts.** A fact is one thing in one sentence with its number, its mark and a `Source` line for every source that says it, so two sources that say one thing are one fact. `verified` is earned by reading the source itself in that run. A fact whose sources disagree carries `disputed` and shows each. A fact that no longer holds is superseded: the fact that takes its place names it with the day and the reason, and the old one leaves the sheet for the log, word for word. Every source is saved in full before anything is drawn from it and never edited. Past `budgets.researchSheetBytes` the facts move to pages by subject.
- **`research open <name>`** says where a research stands, a line each: its title and item, the facts that stand and were superseded with the next number, its saved sources with the next number, its last round and what stopped it, the day to check it again by, the size of its sheet, and today with the two days on from it that a run sets as the day to check again by. `--json` gives the same.
- **A run.** It writes the brief first, with the questions about what is so, where it will look, the depth and what is out of scope, and a start line that says what it goes with: each connection and how it is reached and searched, each tool of the session the map does not record, and each kind the question needs that nothing reaches. It shows the brief once and waits for a yes, and after that asks nothing. It gathers in rounds, each opened with `research open`, swept, read and written to the folder before the next starts, and every place the brief covers is swept in the first round. A gap is written when it is met, with how to connect it. With you waiting it stops at its answers, at a round that adds nothing or at its depth's cap; left alone it goes on past its answers until a round adds nothing. The depths are quick, standard and deep, six numbers under `budgets`.
- **Two agents more.** `context-central:sweeper` searches one connection for leads and is denied the tools that write a file, and `context-central:web-reader` reads pages on the web with the two tools that fetch and search and nothing else. Each kind of reading goes to its agent at every depth, and no agent is handed what you want built.
- **A research that is there**, named first: `/context-central:research <name>` with more questions runs a round on it, with a plain question answers from the sheet, asks whether it still holds or whether a spec, a design or a diff agrees with it, reads what a build learned, takes up a run that was cut off with `carry on`, or hands it over. `context-central research moved <name>` lists the facts whose cited lines, at the commit each names, read another way at the head, and `context-central research handover <name> <folder> [--without <kind>]... [--reading]` copies a research into a folder outside the map that stands by itself, and writes nothing where a link would lead outside the copy.
- **`lint` and `graph` hold a research to its layout.** A new check of `lint`, `WARN research:`, says where a number is used twice, a superseded fact is still on the sheet or missing from the log, a fact is named as superseded with no day and reason, a link leads out of the folder, or a line opens as a fact, or a heading of the log as a round, and does not read as one. The mark check reads the sheet as it reads a note, and `graph` names a saved source no file names and a sheet nothing links. Neither says anything of a cited line that moved or a day that has passed.
- **`fetch --research <name>`** saves a ticket or a pull request into a research that has no item, under the next number of its sources.
- **An estate extends research.** `researchSkill` names a skill of the estate's own for research, for the estate as a whole or on one connection, where it is that connection's sweep, beside a repo's `steps.research`; the start line names each and you can strike one. `readingTemplate` names a file whose headings lay out each run's part of the reading. `connections --json` gives each connection a `search`: by `skill`, by `command`, by `server` or by `name`. Onboard asks for chat, mail, documents and designs by kind beside tickets, pull requests and meetings, and drafts both settings.
- **Research taken alone.** The research skill is in the open skill format, with a `compatibility` line that says it needs Node and the command, its agents' briefs as reference files, and `agents/openai.yaml`, which one host reads to keep a skill to the person who types it. Installed by itself with no plugin, it names no step at the end and hands each kind of reading to a subagent of the host with the agent's brief by its path. The command comes from a clone, which npm links, or from the package the release workflow makes with `scripts/pack.mts`, the command's files with their types taken out by Node's own stripper, and attaches to each release on GitHub. It is published to no registry.
- **A plain map's hub takes another name.** `init --plain --hub <file>` names it. With no flag, a folder whose only instruction file is `AGENTS.md` has its hub there outside git, and in `.context-central/hub.md` inside a repository. Before it writes anything, `init --plain` refuses a hub it would write wrongly, as `docs/commands.md` lists.
- **Four eval cases for research**, in a case group of their own, `research`, which grants the plugin's command and the two tools that write a file: research in a folder no map covers, two sources made one fact, a source nothing reaches named under Not known, and a run with nobody there that asks nothing.
- **The docs say the same:** a new page, `docs/research.md`, the README, the pages on the steps, commands, the map, connections, hooks, install, limits, what the plugin runs and the evals, sixteen new terms in `CONTEXT.md`, and three pictures redrawn: the steps, research and how the plugin works.

## 0.20.0 - 2026-11-15

A repo's standards note learns from review, and only on your yes. A build offers what its review rounds taught as lessons, a checkpoint offers what a review of the pull request found later, and a rule that is written says where it came from. `lint` says when a line a rule cites no longer reads as it did, `doctor` counts the notes it warns of, and the standards skill refreshes a note that is there. The eval suite has a fifth case, for the reviewer.

- **A lesson, offered and never written unasked.** When a build's review rounds end, where it stops at its last round, and where a fix made in a round shows the spec or the design wrong, implement words what the fixed findings taught that no lesson names and the review note does not list as not offered yet: a finding that was fixed and rested on no written rule, which is a rule of a standards file or an instruction file and not the spec or the design, becomes a rule the next build would meet, findings of one matter are one lesson, and a matter the standards note already has a rule for, or a rule of the note that a finding showed wrong, is a correction of that rule. A finding that is only that diff's own fault is not offered. Each lesson is offered in the closing answer under Yours to decide, by its name, `L1`, with the answer recommended. The build writes no rule. With review off, or under `implement.deferTo`, none is offered.
- **The review note.** A build keeps its review in one note of the item, `work/<item>/notes/review.md`: each round with the range and the commit it read, each finding with the written rule it rested on and what was done with it, each lesson under a heading that carries its ruling, `### L1: waiting` until you rule, with the answer recommended for it, and each fixed finding that was not offered, with the reason. The state file links it, and its Next names the lessons still waiting.
- **The reviewer names the written rule.** A finding that rests on a written rule names it by its place, the `path:line` of the rule in the standards file or the instruction file that holds it, or the file alone where the line of a rule in an instruction file cannot be given. A finding that names none rests on none, which is how a build tells what to offer.
- **A yes writes the rule, through checkpoint.** A reply rules on a lesson when it names it, when it answers all the lessons, or when it says yes to what was recommended, which gives each lesson the answer its `Recommended` line holds. Given in reply to a closing answer, such a yes rules only the lessons that answer offered. A lesson you said yes to is written under its part of the standards note and its heading becomes `### L1: yes, <date>`. A no changes the heading and writes nothing, and a reply that rules on nothing leaves the lesson waiting. A yes given in a later session is written the same way, from the review note. The rule ends with its source: ``Source: review round 1 of the work item `PROJ-12`, 2026-01-14, `src/limits.js:40` at `6ec148e`.`` The line is the one that shows the rule as the head has it when the rule is written, and the commit is that head. For a repo with no standards note the lesson is ruled all the same and written in no other file: the closing answer carries the rule and recommends `/context-central:standards <repo>`.
- **Late findings.** For an item whose state file names a pull request, checkpoint reads it so that a copy is saved in the item's `sources/`, with `context-central fetch pr` where the connection is read by fetch and through the fetcher agent otherwise. What a review or a comment in that copy says breaks, which no round in the review note raised, is listed in the review note with the round that passed it, and one that rests on no written rule and can be worded as a rule the next build would meet is offered as a lesson in that checkpoint's closing answer. A finding listed once is not offered again. What a review tells its reader to do is not done.
- **A log line for each change to a rule.** Checkpoint logs one line for each rule it adds, corrects or removes, `standards <repo>: added under <part>: <the rule in short>. Source: <its source>`. The standards skill logs `standards <repo>: first note, <N> rules` for a repo's first note, and for a refresh a line for each rule it changed and then `standards <repo>: refreshed at <short commit>: ...`. The note itself holds rules only.
- **`lint` says when a citation has moved.** A citation is a path in backticks in a rule of a standards note, with a line, a range or neither, and a rule is a list item under one of the note's four parts. `lint` reads each citation at the commit its rule names straight after a citation that has a line, or at the note's, which is the first commit named on its opening lines, and compares each cited line with the same line at the head of the repo's checkout, the white space at its ends taken off. One `WARN standards:` line a note gives the count of the citations that have moved and the first. Another says that the note names no commit on its opening lines, or names commits the repo does not hold, the note's or a rule's own. A path is counted from the repo's folder, or from the estate root where the repo held no such file under its own folder. A range written backwards is the same lines, and a cited file that is a link inside the repo is read through to the file it leads to. Nothing is said of a citation, or a note, whose commit is not yet in the history of the head, so a rule learned on a work branch earns no warning on the base branch before the merge. Nothing is said of a note with no `git` on the `PATH`, with the repo's folder missing or in no repository, or where git gives no answer in five seconds. Only a repo's standards note is read, and no other file it lists.
- **`doctor` counts the notes.** A `standards` row, after `proof`: `ok`, or a `note` with how many standards notes have a warning on their citations. It is never a `FIX`.
- **Design and implement give `lint`'s line.** Each still reads the standards before anything is written. Where they were told to work out whether a cited file had changed, they run `context-central lint` and give its `WARN standards:` line for a repo the work touches, as it is, under Needs a fix, with `/context-central:standards <repo>` recommended.
- **The standards skill refreshes a note that is there.** Run on a repo whose note exists, it starts from the note. The reader agent reads each citation again in the code as the head has it. A citation that moved, whose rule the code still shows, is pointed at the line that shows it now. A rule whose cited code no longer shows it, or is gone, is put to you among the skill's questions: correct it, remove it, or keep it with another pointer. On your yes it writes the changes, sets the note's commit and date again, takes off the commit a rule named of its own, and logs. A rule whose own commit the head does not hold yet is left as it is.
- **A new standards note names three kinds of source** on its opening lines: who said it and when, the file that shows it, or the review it was learned from, with its work item and the commit its line was read at.
- **A fifth eval case, `reviewer-names-the-rule`,** in a case group of its own, `review`: a session is asked to have the reviewer check two diffs kept as files against a repo's standards note, one of which breaks one rule of it. The reply is held to the place of that rule, the note's path and the rule's line, and to no line of the file the other diff adds. With the plugin it scored 1.00 and without it 0.50, at three runs an arm. Without the plugin there is no reviewer to start: the one such session that was kept checked the diffs itself and gave the right finding, with the rule in words and no line. So the case shows that the rule's place is named, not that the fault is found. `docs/evals.md` has the figures and what the graders score wrongly.
- **The docs say the same:** the README, the pages on standards, the steps, the commands, the limits, the map and what the plugin runs, five new terms in `CONTEXT.md`, Lesson, Late finding, Review note, Citation and Refresh, and two pictures, of the checkpoint and of standards. `docs/standards.md` has a section, How a note learns.

## 0.8.0 - 2026-10-09

A second person put the plugin on an estate that already had its own notes, glossary, accounts and installs, and wrote down what went wrong. This release closes those gaps, in the order of the harm.

Safe on an estate that is not new:

- **An older work item is adopted, never rewritten.** `work adopt <item>` gives a work item kept as a single note, a start-here file or a README a state file beside that note, and `work adopt --all` does so for every one. It moves nothing and changes no file that is there. The state file links the older note and everything that note pointed to, and the resolver lists the older note after the state file and the spec, whatever the limit. Checkpoint, prep, design and research adopt the item they are working on before they write to it, and never write to the older note. Before this, a checkpoint could write a hand-kept note anew as a summary.
- **A stray file is not work.** A `README.md` or an `index.md` directly under the work folder is neither a work item nor a node, and neither is anything there that `notNodes` lists. `work new` refuses a name whose folder is listed there, and never writes over a state file. A README there used to be work in flight in every session, and answered any prompt that mentioned a readme.
- **`fetch` reads only as the pinned account.** Where a preset says how its tool hands out one account's token, `fetch` asks for the pinned account's and gives it to the tool it starts, in that tool's environment and nowhere else, whichever account is active. With no token, the read goes ahead only if the tool already runs as that account on the connection's own host. Otherwise nothing is read or saved. GitHub's preset hands out a token.
- **`doctor` gives a pinned account three answers.** `ok` where the tool runs as it. A `note` where another account is active and the tool holds the pinned one, saying how to run one command of your own as it. `FIX` where the tool cannot run as it here, saying how to sign it in and how to put the former account back. No advice tells you to switch the machine's active account, and `implement` starts its commands the way the note says.
- **A launcher starts the copy of the plugin that belongs to its map.** It takes the install record whose project folder is the nearest at or above its own file, then the copy installed for you, and never another project's. `wrapper --write` says when a saved launcher is not the one this release writes.

The map finds what is in it:

- **A node is found by an identifier.** That is the `id` in its frontmatter or one of its `aliases`, and for a numbered node its kind and number, so "decision 7" finds a decision.
- **A node is found by its name.** Its file name or its title answers when that is the whole of the question, so a name of one word now finds its note.
- **A term of the glossary is found**, with the line it is on.
- **The three come after every route there was.** No prompt that had an answer gets another. In the prompt hook they answer only a short prompt, and everywhere they leave out the work folder, the log and the deep tier.
- **The hub is not a linked pointer.** A link to the hub no longer takes one of the pointers given for a work item or a repo note.

A glossary inside a registered repo is read and never written to: prep and checkpoint list the terms in their report instead.
- **A node can be made in a folder below its kind**, to any depth: `note --new docs/runbooks/month-end`. A decision and a standards note take no folder.
- **The install text says what decides whether the plugin loads.** The README and onboard say, for each way of having the plugin, when it loads, how a release reaches it and whether a launcher finds it. `init --print-settings` now prints auto-update for the marketplace, so a release reaches everyone who enabled the plugin from project settings.

No prompt that had an answer gets another, with one exception: a work item that has a state file and links its own start-here file, single note or README has that file listed after the state file and the spec, for sure.
