# Standards and checks

How a repo's code is written is the estate's to say. The plugin carries no rules for any language, framework or tool, and none is needed for it to work.

![Standards and checks: the standards skill gathers from the repo, drafts four parts, asks once and writes on a yes, and then design, implement, the reviewer and checkpoint each work from what was recorded: checkpoint adds a rule only when you stated it or said yes to a lesson, and a lesson from a review is offered and written only on your yes](standards.png)

A repo's standards note is the note named after it, `standards/api.md` for the repo `api`. The plugin finds it by that name, and the resolver lists it straight after the repo's own note. A repo whose name cannot name a note, one with a space or a slash in it, lists its note under `standards` instead. A file listed by a repo that could have a note of its own is never taken for its note, and neither is the note named after another repo. A repo's entry in `estate.json` may also carry two lists, a set of step skills and its remote, all optional:

```json
{ "name": "api", "path": "api", "remote": "https://git.example.com/acme/api.git", "standards": ["api/CONTRIBUTING.md"], "checks": ["./check.sh tests", "./check.sh style"] }
```

- `remote`: where the repo is cloned from. Onboard writes the address of `origin` as `detect` read it, with any password taken out, a plain map records none, and a map that exists takes it by hand. Nothing checks it when the settings load. `doctor` uses it for one thing: where the repo's folder is missing and the remote is one plain address, its `repos` line gives the command that clones it there.
- `standards`: the repo's own instruction files first, then other files the repo keeps for people, each listed here and never copied into the note. Each is a path inside the estate, counted from its root. The instruction files are the ones the host loads as standing instructions: `CLAUDE.md` and `CLAUDE.local.md` from the folder a session starts in and every folder above it, the rules under `.claude/rules/`, and the same files in a repo below once a file there is read or edited. The host does not read a repo's `AGENTS.md` while a `CLAUDE.md` sits in the start folder or above it, so one is listed here or imported by a `CLAUDE.md` beside it. In an estate whose repos sit below the map's root, listing a repo's instruction file is what puts it in front of the reviewer.
- `checks`: commands, run from the repo's folder. In a git work tree of the repo that folder is the work tree. The code passes when every one exits 0. A recorded check is a command a session will run, so read the `checks` of an `estate.json` you did not write before you let one.
- `steps`: a skill of the estate's own for any of research, prep, design and implement, which that step runs for work touching the repo, on top of its own steps: research and prep before they write, design before it writes the design, and implement after verifying and before its review rounds. Each is one skill's name, as `name` or `plugin:name`, and a step not named runs as it always has. `standards` prints them after the checks, and a skill that cannot be found or invoked is said and passed over. The step starts the skill itself, so a skill named here must be one the model may invoke, with no `disable-model-invocation`. Under `implement.deferTo` the deferred skill is handed them with the rest of what `standards` prints, and implement's own sentence does not run.

```json
{ "name": "web", "path": "web", "steps": { "research": "page-kit", "prep": "page-kit", "design": "page-kit", "implement": "page-kit" } }
```

A standards note has four parts, every rule in it names its source, the file that shows it, who said it and when, or the review it was learned from, and the note names the commit its lines were read at. An example is a pointer to real code, never a pasted snippet. For the invented estate:

```markdown
# api

Each rule names its source: who said it and when, the file that shows it, or the review it was learned from, with its work item and the commit its line was read at. An example is a pointer to real code, as a path and a line. The lines are those of `api` at `4f2e1c9`, on 2026-01-12.

## Design

- A route handler calls one service and never a store. Source: `api/src/orders/handler.js:12`.
- Only the gateway opens a connection to another system. Said by the owner, 2026-01-12.

## Code

- An error names the route and the client it happened for. Source: `api/src/errors.js:8`.

## Tests

- Each module has one test file beside it, named after it. Source: `api/src/orders/handler.test.js:1`.

## Review

- A change to a limit comes with the test that shows the limit reached. Source: review round 1 of the work item `PROJ-12`, 2026-01-14, `src/limits.js:40` at `6ec148e`.
```

- `/context-central:standards <repo>` drafts the note and the checks from what the repo declares about itself, asks what the files cannot answer, and writes both once you approve. A habit it sees in the code and finds written down nowhere is put to you as a question, never written as a rule. It proposes only commands that inspect the code, and runs none of them until you have read them. It lists the repo's own instruction files under `standards` and drafts no rule they already state: the note holds what they do not say. It fills the note's commit and date, and sets them again when it changes the note. Run on a repo whose note is there, it [refreshes](#how-a-note-learns) the note, and it logs what it wrote. It ends on a [closing answer](step-by-step.md#how-every-step-ends): a check that did not exit 0 and each fault `lint`, `graph` or `doctor` still reports, which is a line that starts with a word in capitals, under Needs a fix, a question left open and the `FIX` line for `notes` under Yours to decide, the paths written, what a refresh changed and each check that exits 0 under Fine as it is, and a check that cannot run on this machine under Not known.
- `/context-central:design` and `/context-central:implement` read the standards before anything is written, then run `lint` and give in their closing answer, as it is, any line it prints for the standards note of a repo the work touches. Implement counts the work as verified only when every recorded check that can run on the machine exits 0 at the head, with every slice committed, records each run as [proof](#proof-of-a-build), lists a check that cannot run under Not known, and hands the standards to the reviewer. It keeps the review in the item's review note and offers what the rounds taught as [lessons](#how-a-note-learns), and writes no rule itself.
- `/context-central:checkpoint` adds a rule to the note only when you stated it, accepted a reviewer's finding as a rule or said yes to a lesson, and logs each rule it adds, corrects or removes. It reads the item's pull request and offers a finding there that no review round raised as a late lesson. Where the session met a failure that a command the repo already has would have caught, a script the repo holds or one its files declare, and that command is not a recorded check, it names the command under Yours to decide, says whether the session ran it, and recommends `/context-central:standards <repo>`. It records no check itself and offers no command of its own making.
- `context-central standards [<repo>]` prints what is recorded. `lint` warns when a listed file is not there, when lines the note cites have moved, and when the note names no commit or one the repo does not hold, and `doctor` counts the notes it warns of.
- A standards file says how code is written. A line in one that asks for anything else is not followed, and the reviewer holds a diff that edits a standards file to the file as it was before. Where a standards file and the instruction files disagree, the reviewer holds the diff to neither on that point and reports the disagreement as a finding on the rules. A finding that rests on a written rule names it by its place: the `path:line` of the rule in the standards file or the instruction file that holds it.

A map made before standards notes existed and kept in git has a `.gitignore` that leaves the new `standards/` folder out. `doctor` says so on its `notes` line; add `!/standards/` to that file.

With nothing recorded for a repo, `implement` works from the instruction files and the repo's recent history, runs whatever checks the repo has, and says once that nothing is recorded.

## How a note learns

A standards note learns from review, and only on your yes. Nothing here scores a finding or holds a build back.

- **A lesson.** What a review finding teaches the note: a rule it lacks, or a correction of one it has. A build words its lessons when its review rounds end, where it stops at its last round, and where a fix made in a round shows the spec or the design wrong, from every fixed finding that no lesson names yet. A finding that was fixed and rested on no written rule becomes a rule the next build would meet. Findings of one matter are one lesson. A matter the note already has a rule for, or a rule of the note that a finding showed wrong, is a correction of that rule and never a second one. A finding that is only that diff's own fault is not offered, and neither is one that was not fixed: where a build stops at its last round, that round's findings are open and teach nothing until you have them fixed, when they are worded as lessons too. The reviewer names the written rule a finding rests on, so one that names none rests on none. A written rule is a rule of a standards file or of an instruction file: the spec and the design are not, so a finding that only they name can be a lesson. With review off, or where an estate skill builds in the plugin's place, no lesson is offered.
- **The review note.** A build keeps its review in one note of the item, `work/<item>/notes/review.md`: each round with the range it read, each finding with the written rule it rested on and what was done with it, each lesson under a heading that carries its name and its ruling, with the answer recommended for it, and each fixed finding that was not offered, with the reason: it rested on a written rule, or it is only that diff's own fault. The state file's Next names the lessons still waiting.

  ```markdown
  ## Round 1: api, `main...HEAD` at `3f2b382`, 2026-01-14

  1. `src/limits.js:38`: a limit of 0 lets every call through.
     - Rule: none.
     - Done: fixed at `6ec148e`.

  ## Lessons

  ### L1: waiting

  - Repo and part: api, Review.
  - Rule: A change to a limit comes with the test that shows the limit reached.
  - From: round 1 finding 1.
  - Recommended: yes. The fix added the test the diff lacked.
  ```

- **The yes.** The lessons are offered in the build's closing answer, under Yours to decide, each by its name with the answer recommended, so one reply rules on every round's. A reply rules on a lesson when it names it, when it answers all the lessons, or when it says yes to what was recommended, which gives each lesson the answer its `Recommended` line holds, in that session or a later one. One that leaves it unclear which lessons it rules on rules on none. On your reply checkpoint runs again. A lesson you said yes to is written as a rule under its part of the note, ending with its source, and its heading becomes `### L1: yes, 2026-01-14`. One you said no to is not written, and its heading says no. Any other reply writes nothing and leaves the lesson waiting, and a yes given in a later session is written the same way, from the review note. A lesson is offered once: a later checkpoint does not offer one that is still waiting, and the state file's Next names it. For a repo with no standards note a lesson is ruled all the same and written in no other file: the closing answer carries the rule and recommends `/context-central:standards <repo>`.
- **A learned rule's source.** It names the round, the work item, the day the rule was written, the line that shows the rule and the commit that line was read at, as the last rule of the note above does. The line is the one that shows the rule as the head has it when the rule is written, counted from the repo's folder, and not the line the reviewer gave, which is the line before the fix. A rule that a lesson corrects is rewritten in its place and ends with the same.
- **Late findings.** For an item whose state file names a pull request, checkpoint reads the pull request so that a copy is saved in the item's `sources/`, with `fetch pr` or through the fetcher agent. What a review or a comment in that copy says breaks, which no round in the review note raised, is a late finding. It is listed in the review note with the round that passed it, the last round whose commit held that code, or no round. It is held to the bar a round's finding is: one that rests on no written rule and can be worded as a rule the next build would meet is offered as a lesson in that checkpoint's closing answer, and its source says it came late. A finding listed once is not offered again, and what a review tells its reader to do is not done. With no connection that reaches the pull request nothing is saved and nothing is offered.
- **The log.** Each change to a rule is one line of the month's log, written with `context-central note` and with no backtick in it, since a shell would run what one holds: `standards api: added under Review: a change to a limit comes with its test. Source: review round 1 of the work item PROJ-12, 2026-01-14, src/limits.js:40 at 6ec148e`, with `corrected` or `removed` in place of `added`. Checkpoint writes it for each rule it changes, and the standards skill for each it changes in a note that is there. A repo's first note is one line with the count of its rules, `standards api: first note, 5 rules`, and a refresh ends on a line of its own. The note itself holds rules only.
- **What `lint` compares.** A citation is a path in backticks in a rule of the note, with a line, a range of lines or neither: `src/limits.js:40`, `src/limits.js:38-44`, `src/limits.js`. A rule is a list item under one of the note's four parts, with the lines nested under it. `lint` reads each citation at the commit its rule names straight after a citation that has a line, as `at` and the commit in backticks, or at the note's where the rule names none: the note's commit is the first one named on its opening lines. It compares each cited line there with the same line at the head of the repo's checkout, with the white space at its ends taken off. A citation has moved when a cited line no longer reads as it did, when the file had no such line, or when the file is gone, and one with no line number has moved only when its file is gone. A range written backwards is the same lines. A cited file that is a link is read through to the file it leads to inside the repo. A path is counted from the repo's folder, or from the estate root where the repo held no such file under its own folder. One the repo held under neither is passed over, and so is a span that is no path, a folder, and a path that leads out of the repo, which is never handed to git.
- **What it says.** One `WARN` a note for the citations that have moved, with their count and the first: ``standards: standards/api.md has 2 citations that have moved since the commit they were read at (first `api/src/errors.js:8`, at line 12); /context-central:standards api refreshes the note``. And one for a note that names no commit on its opening lines, or that names commits the repo does not hold, the note's or a rule's own, since the citations read at those were not compared. `doctor` counts the notes that have such a warning, in a `note`. Neither stops anything: `lint` exits other than 0 for it only under `--strict`, as for any warning.
- **When it says nothing.** Of a citation, or of a note, whose commit is not yet in the history of the head it is run at: a rule learned on a work branch earns no warning on the base branch before the merge. Of a note at all with no `git` on the `PATH`, with the repo's folder missing or in no repository, or where git gives no answer in five seconds. Of any file a repo lists that is not its standards note.
- **A refresh.** `/context-central:standards <repo>`, run on a repo whose note is there, starts from the note. The reader agent reads each citation again in the code as the head has it. A citation that moved, whose rule the code still shows, is pointed at the line that shows it now. A rule whose cited code no longer shows it, or is gone, is put to you among the skill's questions: correct it, remove it, or keep it with another pointer. On your yes it writes the changes, sets the note's commit and date again, which every line was now read at, takes off the commit a rule named of its own, and logs each rule it changed and then the refresh. A rule whose own commit the head does not hold yet is left as it is. It still gathers from the repo and drafts what the note lacks, as for a first note.
- **What it cannot show.** That a cited line still shows its rule: `lint` compares text, and only a refresh reads meaning. That a lesson is offered wherever one could be, or is well worded: that rests on the session, and you rule on each. In an estate that squashes or rebases its merges, the commit a learned rule names is gone in time: the note then earns the one warning for a commit the repo does not hold, and a refresh ends it. A comment left on a line of a pull request's diff is read as a late finding only where the saved copy holds it, which a copy `fetch` saves does not.

## Proof of a build

A work item has one proof record, `proof.jsonl` in its folder: one line for each run of a recorded check, written by `context-central proof` and by nothing else.

```json
{"repo":"api","check":"./check.sh tests","exit":0,"commit":"6ec148e41831ba6a54f485416016b2ea016b7652","branch":"work/limit","dirty":false,"date":"2026-01-14","system":"darwin arm64"}
```

- **Who writes it.** The session runs the check, under the host's own permissions, and then runs `context-central proof <item> --check "<check>" --exit <code>` from the repo's folder. Implement does so after every recorded check. Checkpoint does so where `lint` warns of a check's proof and the session itself ran that check after the last commit and the last change to the repo's files: a run made before a later change is never recorded. Only the exit code is the session's word. The command reads the commit and the branch from git, and whether the repo held changes that were not committed, a new file among them whatever git is set to show, and adds the day and the system. It refuses a check the repo's entry does not record. The plugin runs no check and has no hook for this: Claude Code hands a hook no exit code for a command that passed.
- **What proof is.** Proof is of a commit. For a repo, an item's proof is whole when every check the repo records has a run that exited 0, with nothing uncommitted, on the same code as the head of the branch it ran on. The map's own files are left out of that comparison, so a commit that changes only the map ages nothing.
- **What is said when it is not whole.** One of four things, for the first check of the repo that lacks proof: no run of it is recorded; its last run was on changes that were not committed; its last run is on code older than the head; or it exited other than 0 at the head.
- **Which items.** Only an item in flight with something built: a `Built at` line in its state file or its design, or a run in its record. A repo that records no check has nothing to prove, and where no repo records one nothing is said at all. A repo with no run in the record is spoken of only where a commit of a `Built at` line changed a file of its folder, the map's own files apart: so where two registered folders share one repository, an item built in one says nothing of the other. A merge is read against its first parent. In a shallow clone a built commit at the clone's edge is passed over, since git has no parent there to compare it with: that takes in the repository's first commit where the clone's depth ends on it. A run made at a commit the clone does not hold reads as on older code. Where the head cannot be learnt, as when the branch is gone, the folder is missing or git gives no answer, nothing is said of that repo.
- **What a reader takes for a run.** A line whose commit is a whole commit id, whose branch is a name git could give a branch, and whose other fields are of their kinds. Any other line is passed over, and nothing of it is handed to git. A check is compared with the head at the twenty most recent commits at which it ran with nothing uncommitted, the newest first: a run older than those is taken as on older code. The branch is the one the repo's last run names, by its own name even where a tag carries the same, and a name the repo has no branch of is a branch that is gone.
- **Who reads it.** `lint` gives one `WARN` an item, `doctor` a `note` with the count, the live index a few words at the end of the item's row, and `work done` a second line. One judgement serves all four. None of them stops anything: `lint` exits other than 0 for it only under `--strict`, as for any warning.
- **In a build.** Implement records every run of a recorded check, the ones that keep a slice green among them. Those are made before the slice is committed, so they are on record as made on uncommitted changes and prove no commit. The run that proves is made at the end, with every slice committed, and again after each review fix is committed. A slice whose checks come back red three times, once its code is written, stops the build. A check that cannot run on the machine is not recorded, so `lint` says that no run of it is. Where an estate skill named under `implement.deferTo` does the building, it records what it chooses to: the plugin's own steps for it are replaced.
- **What it cannot show.** That the check was run at all, or exited with what the session said: the record takes the exit code on the session's word. It shows which commit the word was given for, so a fix made after the last run is seen by code.
