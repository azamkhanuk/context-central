# Commands, skills and agents

What the plugin adds besides its two hooks: the `context-central` command, seven skills and three agents. The hooks are in [What the hooks put in context](hooks.md).

## Commands

Inside a session the plugin puts `context-central` on the Bash tool's `PATH`. [Working from a terminal](terminal.md) says how to run it outside one.

Exit codes: 0 fine, 1 a problem was found, 2 wrong usage.

- **A fault the command did not expect** is one line on standard error and exit 1: `context-central <command>: <what failed, with the path and the system's code>. Set CONTEXT_CENTRAL_DEBUG=1 to see the trace.` With that variable set the trace follows the line.
- **A command that changes the map holds the map's lock for the write.** One that cannot get it within five seconds says `the map is being written by another command, and still was after 5 seconds, so nothing was written; run this again`, writes nothing and exits 1. A lock left by a process that died is taken over once it is thirty seconds old.
- **A command whose reader has closed the pipe**, as in `context-central graph | head -1`, ends quietly with exit 0.

| Command | What it does |
|---|---|
| `help`, `--help`, `-h` | List the commands with a line each, and `--version` last; `<command> --help` gives that command's line |
| `--version` | Print the release, the Node it runs on and the system, in one line. Given after a command it is that command's own flag |
| `config [--get <key>]` | Print the estate settings, or one of them by dotted key |
| `where [--json]` | Show which map covers this folder, where the estate's glossary is and whether the hooks answer here, and in a git work tree the work tree, its main checkout and the drafts folder |
| `work new <item> [--title <title>] [--ticket "<reference>"]\|list [--all] [--json]\|done <item>\|reopen <item>\|adopt <item>\|adopt --all` | Create a work item with its state file, its title and its ticket; list work in flight, or with `--all` every item, as JSON with `--json`; mark an item done, with a second line, `proof: ...`, where its proof is not whole, or reopen it; give an older item, or with `--all` every one, a state file beside its own note |
| `research new <name> [--title <title>] [--item <item>] [--json]\|open <name> [--json]\|moved <name> [--json]\|handover <name> <folder> [--without <kind>]... [--reading]` | Make a research folder in the map, under `research/` unless the estate names another folder as `researchDir`: its fact sheet `index.md`, its brief, its log, its set-aside list, its reading and an empty `sources/`, and print the place of the fact sheet. `--item` names the work item it belongs to on the sheet. Where git tracks the map's settings a second line says whether git keeps the folder or ignores it, and `--json` gives both, as `sheet` and `git`. `open` says where a research stands, a line each: its title, its item, the facts that stand and were superseded with the next number, its saved sources with the next number, its last round and what stopped it, the date to check again by, the size of its sheet against `budgets.researchSheetBytes`, and today with the days `budgets.researchStableDays` and `budgets.researchMovingDays` on from it. For a name that is no research it exits 1 with a line that opens `no research "<name>"` and names the ones the map holds. `moved` lists the facts on the sheet whose cited lines, at the commit each line names, read another way at the head of their repo, says each cited line it could not compare and why, and exits 0 whatever it lists; `--json` gives every cited line. `handover` copies the research into `<folder>`, which lies outside the map and is not there yet or is empty: the sheet with its `item` line left out, its pages, the brief, the log, the set-aside list and the saved sources, with each file of the item's own `sources/` that the research links copied in under `sources/item-`. `--reading` copies the reading too. `--without <kind>`, which may be given more than once, leaves out the saved sources of that kind and names the facts that rest only on them. It writes nothing where a link would lead outside the copy |
| `resolve <query...> [--max N] [--json] [--absolute]` | List the notes behind a work item, a link, a repo name or free text, or else the node an identifier or a name finds, the glossary for a term or the notes that mention a code name, and say which ticket named has no work item |
| `index [--absolute] [--json]` | Print the live index of work in flight, each row ending with words on proof where the item's proof is not whole. `--json` gives each item `proof`, those words or null |
| `hook <session-start\|user-prompt-submit>` | The hook entry point: JSON on stdin, JSON on stdout. It always exits 0, and a failure is one line for the person. Claude Code gives it 15 seconds at session start and 10 at a prompt |
| `graph [--json] [--strict]` | Report broken links, orphan nodes, and deep files and evidence nothing points to |
| `lint [--json] [--strict]` | Check the hub, state files, nodes, evidence and index against their budgets, and that each repo's standards files and a glossary the estate names exist. It warns for an item in flight whose proof is not whole, `proof: <item> in <repo>: ...`, and once for a note whose claims marked `verified` name no source, `mark: <note> has 3 claims marked verified that name no source (first at line 12)`. It warns once for a repo's standards note whose cited lines have moved, ``standards: <note> has 2 citations that have moved since the commit they were read at (first `api/src/errors.js:8`, at line 12); /context-central:standards <repo> refreshes the note``, and once where the note names no commit on its opening lines or names commits the repo does not hold. An entry of the map that cannot be read is an error too, `read: <path> <why>, so the listings pass over it`: a folder or a note with no permission, a link that leads nowhere where a note would be listed, a folder where a note would be read. Nothing under a folder `notNodes` lists is one |
| `doctor [--json]` | Check the setup: Node, settings, hub, lint, links, repo folders, git ignore rules, note folders against git, evidence against git, drafts left in work trees, proof, the citations of standards notes, legacy hooks, copies of the plugin loaded twice, connections |
| `note <text...>` | Append a dated line to this month's log |
| `note --new <kind>/[<folder>/]<name> [--title <title>]` | Create a node from a small template, in a folder below its kind when one is given |
| `draft <path>...` | Print the file to use for each file of the map named: the map's own, or in a git work tree a draft at the same place under the work tree, copied from the map's file where there is one and kept up to date until it is edited. For a file the map does not hold yet it makes the folder in the work tree and writes no file. A path is counted from the map's folder, or is an absolute path inside it |
| `take [--over <path>]...` | Put the work tree's drafts into the map and remove them from the work tree. A draft is kept, with the reason, where the map's file changed after it was drafted or the map holds the file and the draft was not made from it; beside it `take` leaves a copy of the map's file as it now is, to compare with, and `--over` takes the draft once the two are compared. A draft that is in the map and cannot then be removed is kept too, in a line of its own, and the drafts after it are still taken. Two work trees that take a draft of one file at the same moment end with one `took` and one `kept`. In the main checkout there is nothing to take |
| `slice <file> --toc\|--heading <text>\|--lines <a>-<b>\|--grep <regex> [--context N] [--max-bytes N]` | Read part of a large file: its headings, one section, a line range, or matches with `--context` lines around each (2). The output is cut at `--max-bytes` (20,000) |
| `fetch ticket\|pr "<reference>" --item <item> [--connection <name>] [--repo <repo>]` | Read a ticket or a pull request with the command of its connection's preset, save the full text under the item's `sources/`, then print a digest. With no reference, `fetch ticket --item <item>` reads the item's own ticket. `--research <name>` in place of `--item` saves under the `sources/` of a research that has no item, and is refused for one that has, whose ticket or pull request is saved with its item. `--check` in place of either tries the connection and saves nothing |
| `connections [--ticket "<reference>"\|--pr "<reference>"\|--item <item>] [--json]` | List the connections and how this machine reaches each. With a ticket, a pull request or a work item named, only the connection it belongs to: one of the three at a time, since they do not combine. `connections --presets [--json]` lists the presets this version carries and what each takes |
| `evidence add <file> --item <item> [--as <what>]` | Copy a file into the item's `evidence/` under a dated, cleaned name, never overwriting. The folder is for what is not text, and the command takes any file and never opens one |
| `proof <item> --check "<check>" --exit <code>` | Record what a recorded check exited with, as one line in the item's proof record, `proof.jsonl` in its folder. Run it from the repo's folder, straight after the check. Only the exit code is taken on the session's word: the command itself asks git for the commit, the branch and whether the repo holds changes that are not committed, the map's own files left out, and adds the day and the system. It refuses a check that the repo's entry does not record, and from a git work tree it writes straight into the map, with no draft |
| `standards [<repo>] [--json]` | Print a repo's standards files as absolute paths, its standards note first and marked, with a mark on one that is missing or a folder, and its recorded checks with the folder they run from, which in a git work tree of the repo is the work tree, then the skill it names for each step, where it names any |
| `detect [dir] [--json]` | Report what can be read from disk before asking anyone: whether the folder is a git work tree, repos, instruction files, key patterns, tools, accounts and connection candidates |
| `init [dir] --from <answers.json> [--dry-run]` | Write a new map from an answers file, never overwriting |
| `init [dir] --plain [--dry-run]` | Write a plain map with no answers file, never overwriting: inside a repository the map in `.context-central/` with its hub in `CLAUDE.local.md`, both named in the checkout's own `.git/info/exclude` so that git shows nothing new, and from a git work tree in the main checkout; in a folder that holds checkouts the root layout with each registered. It records no connection. It refuses a repository where git tracks `CLAUDE.local.md`. `--dry-run` lists every file it would write or change and writes nothing |
| `init --print-settings` | Print the settings that enable the plugin for a map, with auto-update on for its marketplace |
| `wrapper [--write]` | Print a launcher for running the CLI from a terminal, or save it in the map with one for cmd. A launcher already there is kept, and said to differ when it is not the one this release writes |
| `budget [dir] [--json]` | Show what a session started in a folder loads at launch from instruction files |

About `doctor`:

- It prints one line per check: `ok`, `FIX` with what to do, or `note` with something worth knowing. It exits 1 only if something needs fixing.
- With no `git` on the `PATH`, the six checks that ask git (git, notes, evidence, work trees, proof and standards) each say as a `note` that they were not checked, and the others decide the exit code.
- Its proof check is `ok`, or a `note` with how many items in flight lack proof, which `lint` names. It is never a `FIX`.
- Its standards check is `ok`, or a `note` with how many standards notes have a warning on their citations, which `lint` names. It is never a `FIX` either.
- Its repos check says `FIX` for a registered repo with no folder. Where the repo's entry carries a `remote` that is one plain address, and its `path` is plain too, the line gives the command that clones it there, to be run from the estate root: `git clone <remote> <path>`. A remote with a password, a space, a quote or any mark a shell reads is named as not one plain address and is never printed. The plugin clones nothing.
- Its lint check says `FIX` where `lint` has an error, an entry of the map that cannot be read among them.
- Its connections check holds one thing to be a fault: a pinned account that the tool cannot run as here. Another account being active is a note where the tool holds the pinned one. A tool that is not installed, and a map with no connection, are notes too.
- Its work trees check names each git work tree of the map's checkout in which drafts wait, with how many, and says when the map itself sits in a work tree where git ignores it. [In a git work tree](map.md#in-a-git-work-tree) says what a draft is.
- Its hooks check looks for hooks from an earlier tool that would resolve the same prompts a second time.
- Name those hooks in `estate.json`, for example `"legacyHooks": ["old-resolver.mjs"]`. The list is empty by default, and the check then passes.
- A hook command that contains one of those strings counts when it is in the estate's own `.claude/settings.json` or `.claude/settings.local.json`, or in your user settings and pointing at this estate's root.
- Its copies check says `FIX` where more than one copy of the plugin loads in the estate's folder, as with `context-central@azamkhanuk` and the `context-central@context-central` installed before 0.14.0. A copy loads where it is installed for you or for that folder, and the settings that apply there enable it. Each hook would run once for each copy. The fix names the uninstall command for every copy but the one from the author's marketplace, with the folder to run it from where the copy was installed for one folder.
- A copy installed for you can be kept off in one folder: `"context-central@context-central": false` under `enabledPlugins` in that folder's `.claude/settings.json` turns it off for everyone who opens the map there, except a person whose own `.claude/settings.local.json` turns it back on.

## Skills

Typed with the plugin prefix. All but the last run only when you invoke them; `checkpoint` may also be picked up by the model. The five that do the work are walked through in [A piece of work, step by step](step-by-step.md). Every skill ends on a [closing answer](step-by-step.md#how-every-step-ends) in four groups.

| Skill | What it does |
|---|---|
| `/context-central:onboard` | Detects the estate, asks what is unsettled, writes the map, proves each connection, runs `doctor` |
| `/context-central:standards <repo>` | Drafts one repo's standards note and its checks from what the repo declares, asks what is unsettled, writes both on your yes. Run on a repo whose note is there, it refreshes the note: each citation is read again, one that moved is pointed at the line that shows its rule now, and a rule the code no longer shows is put to you |
| `/context-central:research <question> [item]` | Researches from primary sources, sorts each claim into one of four groups and marks how it is known, writes a note laid out in them, links a note that has no item from the note of each repo it is about, and ends by naming the step that comes next. Writes no code |
| `/context-central:prep <item>` | Reads the item's ticket, then turns the conversation and research into the item's `SPEC.md` and a short tracker brief, or revises the spec that is there |
| `/context-central:design <item>` | Reads the spec, the repo's standards and the code, and writes the item's `DESIGN.md`: the modules, their interfaces, each choice with its reason, the slices in order, the checks beyond this machine and what is cut if time is short. It gives `lint`'s warning for a repo's standards note as it is. Optional, and approved by starting the build |
| `/context-central:implement <item>` | Builds from the state file, the spec and the design when there is one, one slice at a time, following the estate's settings for tests and review, the repo's standards and its recorded checks, and recording each run of a recorded check with `proof`. It keeps the review in the item's review note and offers what the rounds taught as lessons, and writes no rule itself. Stops and asks when a slice's checks have come back red three times, when the last review round allowed, the third unless set, still brings a finding to fix, or when a slice or a fix shows the spec or the design wrong |
| `/context-central:checkpoint` | Writes the session back: state file, lasting lessons, the session's terms in the glossary, the rules you stated and the lessons you said yes to in the repo's standards note, a log line for the item and one for each rule changed, then `lint` and `graph`. It reads the item's pull request so that a copy is saved, and offers a finding there that no review round raised as a lesson. It offers as a check a command of the repo's own that would have caught a failure the session met, and records none |

## Agents

| Agent | What it does |
|---|---|
| `context-central:reader` | Reads the paths it is given and returns short findings with `path:line` references. Does not load `CLAUDE.md` |
| `context-central:fetcher` | Fetches one ticket, PR, thread or meeting through the connection it is given, saves the full text to `sources/` first, returns a digest and the path. Only reads from external systems, and does not load `CLAUDE.md` |
| `context-central:reviewer` | Reviews a diff against the spec, the estate's standing rules, and the design and the repo's standards files when it is given them; where the rules disagree it holds the diff to neither and reports the disagreement. A finding that rests on a written rule names it by its place. Never edits |
