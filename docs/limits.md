# What it does not do

- Its own commands never post to a tracker or a code host. The fetcher holds every tool of the session, and only its brief keeps it to reading and to the one path it saves at. A skill may post through a connection only where your write rules allow it and you approve the exact text.
- Its own `fetch` reads only with the command of a preset. A connection with no preset is read by a session, through its server or your own command. The plugin never runs a command that `estate.json` names. What it puts into a preset's command from a reference or from the settings is one word that does not start with a dash, so that nothing reaches the tool as a flag.
- Of the presets' read commands, only GitHub's has been run against the real tool. Jira's and Azure DevOps's were written from their vendors' documentation and tried against stand-ins. `fetch --check` shows whether one works for you.
- A pull request read by `fetch` holds what the preset's tool returns. Where that leaves out a review's line comments, the fetcher can read them through a server that offers them. Checkpoint looks for late findings in the copy that is saved, so a comment left on a line of the diff is read as one only where that copy holds it, which a copy `fetch` saves does not.
- On Windows it does not start a tool that is installed only as a `.cmd` or a `.bat` file. `fetch` says so, and a session reads that connection through its own shell or a server.
- It does not link or copy nodes into the checkouts. Nodes are reached by pointer. A draft in a git work tree is one file on its way to the map, not a copy of the map.
- Onboard does not set a map up from a git work tree. The hub and the settings that enable the plugin belong to the main checkout, so it stops in a work tree and names it. A plain map is the one map made from a work tree, and `init --plain` makes it in the main checkout.
- It does not follow a link in the map. A link among the notes is passed over, and `lint` names one that leads nowhere. A node folder that is itself a link to a folder is read, and a file that is a link is written through, so the link stays.
- It does not hold the map's lock for a write that lasts longer than thirty seconds. A lock that old is taken for one left by a process that died, so a command stopped that long in the middle of its write, as on a machine that sleeps, may write beside another.
- It does not delete or rename a file of the map through a draft.
- It does not make one map of a map that is partly in git. Where git tracks some of the map's files and not others, a work tree holds its own copies of the tracked ones: `draft` gives those, `take` leaves them alone, and the commands and the hooks go on reading the main checkout's. The live index counts what waits without asking git, so there it may count a tracked file that `take` and `doctor` rightly pass over. Keep a map wholly in git or wholly out of it.
- It does not give a root layout's map a draft. A map above the repositories is outside them, so a session in a repo's work tree writes it as a session in that repo does, under the host's ordinary permission. A map laid out at the root of a repository and kept out of git is not reached by a host's editing tools from a work tree: write that one from the main checkout, or use the inner layout.
- It has not been shown what a sandboxed shell makes of the plugin's writes to a map in the main checkout from a git work tree.
- It does not move or rewrite the files of an older item. Adoption lays a state file beside them and changes nothing else.
- It does not find a pull request written as a repo and a number. A link finds its work item once the item's state file or notes hold it, which checkpoint writes.
- It does not write to a glossary inside a repo, and it does not turn an estate's own glossary into its entry format.
- It does not check where the plugin is enabled. `doctor` cannot tell you that a session started inside a repo is not given the plugin, or that a folder has not been trusted.
- It does not renew a launcher you saved. `wrapper --write` says when one differs, and the renewing is yours.
- It does not ingest meetings on its own: the fetcher reads one when asked. It ships no workflows.
- Its eval suite is a measure taken by hand and gates nothing. It is nine cases on one model and one invented estate, with no case for a checkpoint: a run's sandboxed shell would not start the plugin's own command when it was tried. The first five were run three times an arm. The four research cases were run with the plugin alone, once each or a few times, and need the plugin's `bin` folder first on the `PATH` the host is started with; their group grants no `git`, so their facts name no commit. [The eval suite](evals.md) lists what it cannot show.
- It carries no coding standards of its own, for any language. A repo's standards are what the estate wrote in its standards note, and its checks are the commands the estate recorded.
- It writes no rule into a standards note without your yes. A lesson from a review is offered, in a build's closing answer or a checkpoint's, and written only when you say yes to it. It gives a finding no severity and keeps no count of them.
- It does not judge whether a note is true. `lint` and `graph` check size and links, and `lint` that a claim marked `verified` names a source: a path with a line number, a web address, a link to a file or the name of a saved source, on the claim's line or on a line nested under it. It does not read the source, and a line that only talks about the mark is counted as a claim. Of a standards note it compares the text of each cited line, at the commit the rule or the note names, with the same line at the head: it does not judge whether the line still shows the rule, which only a refresh by the standards skill reads.
- It never runs a recorded check, and it does not know that one was run. The proof record holds what a session said a check exited with, beside the commit git gave for it. [Proof of a build](standards.md#proof-of-a-build) says what that can and cannot show.
- It holds nothing back for proof that is not whole. `lint`, `doctor`, the live index and `work done` say so, and a merge is still yours.
- It clones no repo. `doctor` prints the command for a repo whose folder is missing, where its entry carries a plain remote.
- On Windows it has not been tried in a live Claude Code session. These are untested on Windows, not known to fail:
  - Nothing has shown that Claude Code fires the hooks there, or that a skill reaches `context-central` from the Bash tool.
  - Nothing has shown what `fetch` does with an answer from a preset's tool there, or what `doctor` and `detect` make of its accounts.
  - Of `doctor`'s check on what git ignores, one case ran there with real `git`: checkouts the map's repository does not ignore.
  - PowerShell 7 has not been tried, and no argument with a space or a special character has been sent through either PowerShell.
  - The cmd launcher's choice of an install by project folder has run there only against a record of a copy installed for the person.
- It does not support a Windows session that has only the PowerShell tool. The skills call `context-central` from the Bash tool, which needs Git for Windows.
- It ships a `bin/` folder, so claude.ai and Cowork do not install it. It is for Claude Code and, from 0.22.0, for the GitHub Copilot command line. VS Code is not covered.
- On the Copilot command line less has been shown, and some things are not there. [On the Copilot command line](install.md#on-the-copilot-command-line) has what was run and how.
  - No skill has been run to its end there with any model, and of the seven only `checkpoint` was loaded. What was run, on Copilot 1.0.116, ran against a stand-in model, which shows what Copilot does with the plugin and nothing of how a model there follows a skill.
  - The six skills you type cannot be started in a run with nobody there: `copilot -p` hands a slash name to the model as typed, and refuses the model a skill kept to the person.
  - The command is not on the `PATH` there, a skill's `allowed-tools` grants nothing, and the plugin's folder is outside what Copilot lets a session use by itself, so Copilot asks, or is told at its start.
  - A hook runs only in a folder you have trusted, and in a `-p` run of a folder nobody trusted none runs.
  - A hub kept as `.github/copilot-instructions.md` or under `.github/instructions/` is given twice at a session's start, once by Copilot and once by the hook, and so is one in a folder that `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` names.
  - After a compaction the live index is not given again: by a report measured on Copilot 1.0.99 and 1.0.100, it starts no session-start hook then. No notice is given on a resumed session, since Copilot does not tell a hook what the notice rests on.
  - The sweeper is not kept from writing by Copilot, which does not read `disallowedTools`. Four agents ask for their model by the name `sonnet`, which has not been tried on GitHub's models, and the web reader's tools were not seen there.
  - It has been run there on macOS alone. The `powershell` line of each hook starts `node` and reads nothing itself, so the program reads the hook's input as the host wrote it. Tests on GitHub's Windows machines hold the line: they start PowerShell 7, which Copilot's help names, and Windows PowerShell 5.1 with it, and give it the hook's input both written to it, as a program that starts a hook writes it, and handed over whole, with a letter outside ASCII in a folder's name and in a prompt. How Copilot starts PowerShell was not seen, and the line has not run under Copilot.
- The research skill alone is in the open skill format, which other hosts read, and has been run only on Claude Code. A host that reads neither its head nor `agents/openai.yaml` may start research of its own accord, and where a host has no subagent kept from writing a file, only the brief's words keep an agent to reading. On Claude Code the sweeper and the reader hold a shell, the sweeper every tool of its server and the fetcher every tool of the session, so there too their briefs alone keep them from writing through the shell or posting. [Where a host cannot hold it](research.md#where-a-host-cannot-hold-it) has the rest.
- The package of the command is attached to each release on GitHub from 0.21.0 and published to no registry. The step that attaches it runs only on GitHub after a merge that raises the version.
- Research does not judge whether a fact is true, or that two facts say one thing: the session does, and `lint` holds the folder to its layout alone. `research moved` compares the text of each cited line and does not read whether the fact still holds.
